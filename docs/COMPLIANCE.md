# Compliance mapping: ISO/IEC 27001:2022 and ISO/IEC 42001:2023

> Generated by scripts/gen-compliance-docs.py; edit that script and regenerate.

jt-ipam is not a certification, and using it does not mean passing ISO/IEC 27001:2022 or ISO/IEC 42001:2023. This document has two parts: the controls jt-ipam already implements and that can serve as evidence (each with a test or setting you can check yourself), and what the adopting organisation is responsible for after deploying jt-ipam.

Only capabilities the code actually has are listed. It was written for 1.0.6; later changes are in the CHANGELOG. For a formal assessment, pin a version or commit and verify in your own environment.

## Where the data is

IPAM data, audit records and the credentials of integrated systems all stay on your own server, and jt-ipam works fully without any cloud service. Data only goes to a service the administrator sets up when an item marked optional below is turned on.

- **Your network (your own servers)**: Users' browsers ↔ jt-ipam server ↔ Network devices and integrated systems, Scan agents (optional), LLM server (optional), Directory and single sign-on (optional), Audit forwarding (optional)
- **Outside**: Cloud AI services (OpenAI-compatible APIs): Not needed; only used if you point the LLM at one
- **Outside**: Notification channels (Email, Telegram, Slack, Teams, webhooks…): Only sent if you turn them on
- **Outside**: Public DNS resolvers (External resolution check of exposed services): Only names under the public domains you list
- **Outside**: Public data (OUI vendor list, Recog fingerprints, GeoIP (optional)): Download only; none of your data is sent

The version check and RDAP lookups only go out when you press their button (GitHub, RIPE, APNIC); installing and upgrading download software from the OS package repositories, PyPI, npm and GitHub.

| Data | Where it is kept, and for how long |
|---|---|
| IPAM data (sections, subnets, IPs, devices, racks, data synced from integrations) | PostgreSQL (database `jt_ipam` by default), kept until deleted |
| Audit records | PostgreSQL; the database only allows inserts (no update, delete or truncate), records are hash-chained, verified every 5 minutes and anchored to `/var/lib/jt-ipam/audit-anchors.jsonl` and journald. Never purged automatically; forward them to a SIEM for long-term retention |
| IP change log, liveness history | PostgreSQL, kept until deleted (the dimming setting only affects the display) |
| ARP tables, switch MAC tables | ARP 30 days and MAC tables 365 days by default (`ARP_RETENTION_DAYS`, `FDB_RETENTION_DAYS`; 0 keeps them forever) |
| Unmanaged-address sightings, external DNS changes, scan agent load | Kept 30, 90 and 7 days respectively |
| AI chat history | PostgreSQL, 90 days by default (adjustable; 0 keeps it forever), can also be cleared by hand |
| IP change assessments | Closed, cancelled or archived plans 180 days; failed or cancelled runs 30 days; each purge is audited |
| Integration credentials and keys | PostgreSQL, encrypted with AES-256-GCM; the key is in `/etc/jt-ipam/backend.env`. API tokens are stored only as hashes |
| Sign-in sessions | PostgreSQL (server side): access tokens 15 minutes, sessions 14 days. Redis only holds rate-limit counters and single-use console tickets (30 to 60 seconds) |
| Console connections (SSH, SFTP, RDP, VNC and others) | Screens and keystrokes are not recorded; session open and close and every SFTP file operation (path, size) go into the audit records. Uploaded files are written straight to the target host, not kept on jt-ipam |
| Uploaded files such as floor plans | `/var/lib/jt-ipam/uploads`, kept until deleted |
| System export files | Password-encrypted (scrypt, AES-256-GCM), spooled in `/var/lib/jt-ipam/transfer`; files older than 48 hours are removed at the next export or import |
| Daily backups | `/var/backups/jt-ipam`, daily at 03:30, kept 14 days; contains the database, `backend.env`, TLS certificates and uploaded files. Encrypted (`.jtbak`) only when a backup passphrase is set in system settings; otherwise plain, so protect it separately |

### Clauses and controls (ISO/IEC 27001:2022)

Numbers follow ISO/IEC 27001:2022 Annex A (the same as ISO/IEC 27002:2022); numbers without A. are clauses of the main text. jt-ipam provides technical evidence; whether a control is met is decided by the adopting organisation through its risk assessment and statement of applicability. ## ISO/IEC 42001:2023: AI features and controls

### AI feature inventory

| AI feature | Purpose | Default |
|---|---|---|
| AI chat | Query the IPAM in natural language; the model reads data through tools | Available once the LLM is enabled |
| Semantic search | Similarity search with an embedding model | Available once the LLM is enabled |
| IP investigation narrative, IP triage card | Turn facts already collected into an explanation | Available once the LLM is enabled |
| Firewall rule change review | Explain the rule differences found by the program | Available once the LLM is enabled |
| AI suggestions in IP change assessment | Suggest to-dos from the assessment result | Available once the LLM is enabled |
| AI review | Review data on a schedule and list findings | Off |
| External MCP | Let external AI clients call jt-ipam tools | Off |

The model endpoint can be a self-hosted Ollama or an OpenAI-compatible API (chosen by an admin). While the LLM is disabled, jt-ipam makes no model requests of its own; AI review has its own switch. External MCP is not affected by the LLM switch: external AI clients use their own models, and access is controlled by the Expose MCP switch, tokens and the MCP key. The results of anomaly detection, rule change detection and IP change assessment are computed by queries, not produced by a model. The intended use is querying and explaining IPAM data and summarising facts already collected; AI answers and narratives assist people and do not make decisions, and every action that changes data needs a person to confirm.

## What the adopting organisation is responsible for

### Information security (ISO/IEC 27001:2022)

- Accounts: set two-factor authentication to required for administrators or for everyone under Sign-in security on the users page, and review exceptions regularly. (A.5.17, A.8.5)
- Leavers: deactivate the account; do not rely on Sign out everywhere (it only ends sessions: the account can sign in again and personal API tokens keep working). Deactivation revokes all sessions and the person's API tokens and refuses every later request, and open consoles close at the next permission check (at most 30 seconds); confirm all of these have stopped working. For accounts that sign in through LDAP, OIDC or SAML, disable the person in the identity provider too; rotate shared credentials the person held (the read-only MCP key, integration account passwords, agent keys). (A.5.18, A.6.5)
- Movers: adjust permission grants and group memberships; permissions are read on every request, so the next request uses the new ones, personal API tokens follow the account's permissions, and open consoles close within 30 seconds if the new permissions no longer allow them. Where needed, use Sign out everywhere so the person signs in again, and check the new permissions. (A.5.18, A.6.5)
- Access reviews: regularly review permission grants, group members, API tokens, console rights and active sessions, using the audit log where needed. (A.5.18, A.8.2)
- Integration accounts: give each integration its own least-privilege account (most only need read access); rotate passwords and keys regularly; replace tokens when expiry notices arrive. (A.5.17, A.8.2)
- Keys and backups: set a backup encryption passphrase and keep it somewhere other than the jt-ipam host; store backups off-site, rehearse restores (including decryption) regularly, and set an RPO and RTO. (A.5.30, A.8.13)
- Audit evidence: forward audit records and anchors to Graylog or a SIEM on another host and configure write-once retention there (forwarding alone does not provide it); restrict who holds database superuser and host administrator rights; review chain verification results regularly; run harden-audit after restoring a backup or when using an external database. (A.5.28, A.8.15)
- Network: open only the inbound ports you need; keep jt-ipam in a management network; use HTTPS for Graylog DSV where possible, and restrict allowed sources when plain port 8088 is required. (A.8.20, A.8.22)
- Scan and certificate agents: assign only the subnets and certificates they need; disable or delete unused agents and rotate agent keys regularly. (A.5.18)
- Updates: follow new releases and upgrade according to the CHANGELOG (the upgrade script backs up first). (A.8.8, A.8.32)
- Management system: risk assessment and treatment, the statement of applicability, training, internal audits and management reviews are the adopting organisation's responsibility. (6.1.2, 6.1.3, 7.2, 7.3, 9.2, 9.3)

### AI management (ISO/IEC 42001:2023)

- AI policy and inventory: decide which AI features to turn on and who owns them, and record the model endpoint and version. (5.2, A.2.2, A.3.2, A.4.2)
- Data flows: choose a self-hosted model or an external API; if you open external MCP, the data an external AI client receives may be passed on to its own cloud model, so assess and approve that flow separately. (A.10.3)
- Model changes: before switching models or changing parameters, run a fixed set of questions as a regression test (tool use, query scope, answers when nothing is found). (A.6.2.4, A.6.2.5)
- Human review: AI answers and review findings are suggestions, not conclusions; network changes go through IP change assessment and its review workflow. (A.9.2)
- Intended use: define the permitted uses of the AI features (such as querying, explaining and summarising facts), their limits (for example, not the sole basis for a security verdict or for attributing responsibility to a person) and when human review is required, and tell users. (A.9.4)
- Impact assessment: assess how wrong conclusions affect people and the organisation, such as attributing a device to the wrong user or a wrong maintenance suggestion causing an outage. (6.1.4, 8.4, A.5.2, A.5.4)
- Incidents: define what counts as an AI incident (criteria), who is notified (users, administrators, affected units), who owns it and the time limits, and how AI mistakes are reported and AI features are paused (the global LLM switch, the Expose MCP switch, revoking tokens). jt-ipam's notification events and channels can deliver the messages; the recipients, criteria and time limits are set by the organisation. (A.3.3, A.8.4)
- Management system: the statement of applicability, training, internal audits and management reviews are the adopting organisation's responsibility. (6.1.3, 7.2, 7.3, 9.2, 9.3)
