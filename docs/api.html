1認證：API 權杖Auth: API tokens認証：API トークン

外部程式一律用 API 權杖，不要用帳號密碼登入拿 JWT（JWT 只有 15 分鐘、是給網頁前端用的）。 External programs should always use an API token rather than logging in for a JWT (JWTs last 15 minutes and exist for the web UI).外部のプログラムからは必ず API トークンを使ってください。ユーザー名とパスワードでログインして JWT を取得する方法は避けてください（JWT は 15 分で切れ、Web UI のためのものです）。

怎麼取得權杖Getting a tokenトークンの取得

登入 jt-ipam → 右上角使用者選單 → API 權杖 → 新增。填名稱、有效天數（1～365，預設 90）、權限範圍，按儲存。 Sign in to jt-ipam → user menu (top right) → API tokens → Add. Give it a name, a lifetime (1–365 days, default 90) and a scope, then save.jt-ipam にログイン → 右上のユーザーメニュー → API トークン → 追加。名称、有効日数（1～365、既定は 90）、スコープを入力して保存します。

明文只出現一次。建立完成的那個視窗是你唯一能看到完整權杖的機會：資料庫只存 SHA-256 雜湊。沒抄到就撤銷重建，沒有別的辦法找回來。 The plaintext is shown once. The dialog right after creation is your only chance to see the full token; only its SHA-256 hash is stored. If you lose it, revoke and create a new one; there is no way to recover it.平文は一度しか表示されません。作成直後のダイアログが、完全なトークンを見られる唯一の機会です。データベースには SHA-256 ハッシュしか保存されません。控え損ねた場合は失効させて作り直すしかなく、復元する方法はありません。

怎麼帶權杖Sending the tokenトークンの送り方

curl -H "Authorization: Bearer jt_prod_xxxxxxxxxxxxxxxx" \
  https://ipam.example.com/api/v1/subnets

權杖首碼 jt_ 會讓後端自動辨識為 API 權杖（沒有這個首碼則當成 JWT 解析）。 The jt_ prefix tells the backend this is an API token (without it, the value is parsed as a JWT).先頭の jt_ によって、バックエンドはこれが API トークンだと判断します（この接頭辞が無ければ JWT として解析されます）。

2通用慣例Conventions共通の決まり

  • 基底路徑：/api/v1。請求與回應預設是 JSON（Content-Type: application/json）；例外會在各節明講（CSV 匯出、multipart 匯入、DSV 純文字、SVG、SSE 串流）。 Base path: /api/v1. Requests and responses are JSON (Content-Type: application/json) unless a section says otherwise (CSV exports, multipart imports, DSV text, SVG, SSE streams).ベースパスは /api/v1 です。リクエストもレスポンスも既定は JSON（Content-Type: application/json）で、例外は各節で明記します（CSV エクスポート、multipart の取り込み、DSV のテキスト、SVG、SSE ストリーム）。
  • 識別碼是 UUID，不是遞增整數。 Identifiers are UUIDs, not incrementing integers.識別子は UUID であり、連番の整数ではありません。
  • 時間一律是 UTC 的 ISO 8601，但寫法有兩種：用 schema 定義回應的端點寫成 2026-07-30T12:34:56.123456Z，直接回字典的端點寫成 2026-07-30T12:34:56.123456+00:00，兩者都可能帶微秒。phpIPAM 相容層的權杖到期時間則是 YYYY-MM-DD HH:MM:SS（UTC）。請用通用的 ISO 8601 解析器，不要比對固定格式字串。 Timestamps are always UTC ISO 8601, written two ways: endpoints with a response schema return 2026-07-30T12:34:56.123456Z, endpoints that return a plain dict return 2026-07-30T12:34:56.123456+00:00, and either may carry microseconds. The phpIPAM layer's token expiry is YYYY-MM-DD HH:MM:SS (UTC). Use a general ISO 8601 parser instead of matching a fixed format string.時刻はすべて UTC の ISO 8601 ですが、書き方が二通りあります。スキーマで応答を定義したエンドポイントは 2026-07-30T12:34:56.123456Z、辞書をそのまま返すエンドポイントは 2026-07-30T12:34:56.123456+00:00 で、どちらもマイクロ秒が付くことがあります。phpIPAM 互換レイヤのトークン有効期限は YYYY-MM-DD HH:MM:SS（UTC）です。固定の書式文字列と照合せず、汎用の ISO 8601 パーサを使ってください。
  • 未知欄位會被拒絕。寫入用的 schema 是嚴格模式（extra=forbid）：多送一個拼錯的欄位會回 422，而不是安靜忽略。 Unknown fields are rejected. Write schemas are strict (extra=forbid): a misspelled extra field returns 422 instead of being silently ignored.未知の項目は拒否されます。書き込み用のスキーマは厳格モード（extra=forbid）です。綴りを誤った項目を余分に送ると、黙って無視されるのではなく 422 が返ります。
  • 部分更新用 PATCH，只送要改的欄位。 Use PATCH for partial updates, sending only the fields you want to change.部分更新には PATCH を使い、変更したい項目だけを送ってください。

10IP 探測IP probeIP プローブ

IP 探測是管理員限定的單次深度識別：由該位址所屬子網路的掃描代理，對目標跑一次 nmap 服務偵測（前面先做反解、NetBIOS、mDNS），再用已安裝的 Recog 指紋庫把結果歸納成作業系統與產品。jt-ipam 伺服器本身不會連到目標。代理要跑的腳本清單寫死在代理程式裡（banner、http-title、http-server-header、ssl-cert、ssh-hostkey、smb-os-discovery、rdp-ntlm-info），伺服器改不了。服務偵測可能觸發 IDS 告警，請只對你負責的主機使用。 The IP probe is an admin-only, single deep identification: the scan agent of the address's subnet runs one nmap service scan against the target (after reverse DNS, NetBIOS and mDNS lookups), and the result is summarised into OS and product using the installed Recog fingerprint database. The jt-ipam server never connects to the target itself. The list of scripts is hard-coded in the agent (banner, http-title, http-server-header, ssl-cert, ssh-hostkey, smb-os-discovery, rdp-ntlm-info) and cannot be changed by the server. 掃描代理與憑證派送代理有自己的通道，用各自獨立的金鑰（X-Agent-Key 標頭）而不是 API 權杖。這些端點是給代理程式用的，一般整合不需要碰；代理端點與安裝腳本大多不在 OpenAPI 裡。 The scan agent and certificate-distribution agent have their own channel, authenticated by per-agent keys (the X-Agent-Key header) rather than API tokens. These endpoints are for the agents themselves; normal integrations don't need them, and most agent endpoints and installers are not in OpenAPI.スキャンエージェントと証明書配布エージェントは専用の経路を持ち、API トークンではなくエージェントごとの鍵（X-Agent-Key ヘッダ）で認証します。これらはエージェント自身のためのエンドポイントで、通常の連携で触る必要はありません。エージェント用エンドポイントとインストールスクリプトの多くは OpenAPI に載っていません。

  • 掃描代理的金鑰只存 SHA-256 雜湊，只在建立（POST /api/v1/scan-agents 回應的 enroll_key）或輪替（POST /scan-agents/{id}/rotate-key，舊金鑰立即失效）時顯示這單次，遺失就只能輪替。 Scan agent keys are stored only as a SHA-256 hash and shown this one time at creation (enroll_key in the POST /api/v1/scan-agents response) or rotation (POST /scan-agents/{id}/rotate-key; the old key stops working at once). If lost, rotate.スキャンエージェントの鍵は SHA-256 ハッシュだけを保存し、作成時（POST /api/v1/scan-agents の応答の enroll_key）または更新時（POST /scan-agents/{id}/rotate-key。旧鍵は即座に無効）の一度だけ表示されます。紛失したら更新するしかありません。
